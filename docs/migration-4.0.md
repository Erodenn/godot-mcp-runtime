# Migrating to 4.0

This page lists every change in 4.0 that can break a client, a prompt or a script written against 3.8.1, and what to do instead. The [v4.0.0 release notes](https://github.com/Erodenn/godot-mcp-runtime/releases/tag/v4.0.0) summarize the release.

## Breaking changes

- Godot 4.5 or later is required. Both GDScript files the server runs open with `@warning_ignore_start`, which older engines cannot parse, so on 4.4 and below every headless operation and the bridge fail to load. CI runs the integration suite on 4.5.1, 4.6.2 and 4.7.2.
- `attach_project` and `detach_project` are gone. Attach mode is now `run_project({ attach: true })`, and `stop_project` ends both kinds of session.
- Every tool now returns one JSON object, as `structuredContent` and as the same JSON in a text block, and every tool declares an `outputSchema`. `take_screenshot` and `render_movie` also return image blocks next to it. Tools that used to answer with a sentence now answer with fields, and a handful of fields were renamed. The sections below list every case.
- Calls that used to report success for something that did not happen now return an error, or lead their payload with a `warnings` entry. The sections below list every case.
- A runtime tool never falls back to another project's session. If no session is current, or the current game has exited, it returns an error that lists the live sessions.
- `run_project` on a second project adds a session instead of stopping the first.
- Input that used to be ignored or half applied is now refused: an unknown `validate` key, a `batch_scene_operations` item with a missing or unknown `operation`, a fractional component on an integer vector, an out-of-range packed integer element, an invalid `search_project` `maxResults`, an `update_autoload` call that changes nothing, and an autoload path holding a double quote or a line break.
- Headless scene edits keep what the file held: an inherited scene stays inherited, an edit inside an instance writes only the property that changed, scene and `ext_resource` uids survive, and a script or exported value that names an autoload is no longer lost. `delete_nodes` refuses a node inherited from a base scene, and `add_node` now lets `properties` win over the top-level `position`, `rotation`, `scale`, `visible` and `modulate`.
- `batch_scene_operations` no longer rewrites every scene it names. The closing save writes a scene only if an operation on it succeeded and no `save` item has written it since. A `save` item with `newPath` onto a scene the batch has already changed and not yet written is refused as that item's error, because it would discard those changes.
- The server runs one runtime operation at a time. `run_project`, `switch_project`, the four runtime tools and the profiling tools go through one queue, so calls issued in parallel wait their turn, and a call that waits 30 seconds returns an error naming the operation it waited behind. `stop_project` does not queue: it ends the session at once, and the runtime call it cut off fails saying the session was stopped. The time a `run_project` waits for its turn comes out of its bridge wait, and a start left with under 10 seconds for the bridge is refused before anything is stopped or launched. `profile_project` holds the queue for its whole window: a `simulate_input` sent alongside it no longer runs during the capture. Use `start_profiler`, `simulate_input`, `stop_profiler` to drive the game while it is profiled.
- `profile_project` accepts a window of at most 30 seconds, down from 60, so the call answers inside a client's 60 second request timeout. `start_profiler` still takes up to 60.
- A number written to an integer must be finite, whole and within the range a JSON number carries exactly (up to 2^53). After an `int` property is assigned it is read back. A value outside 32 bits that the property did not keep is an error that leaves the property as it was. A value inside 32 bits that the property's setter changed or ignored (`z_index` above 4096) is a success led by a warning that names both numbers. Both used to be stored wrapped, saturated or truncated under a plain success.
- `list_autoloads` returns one entry per name, the assignment the engine keeps. It used to list a name once per line that assigned it. `remove_autoload` removes every assignment of the name and `update_autoload` edits the one the engine keeps.
- Path parameters are stricter in three places and looser in two. A file or folder name that ends in a dot or a space or is a Windows device name (`NUL`, `con.txt`, `COM1`), a colon outside the drive prefix, and a path to write that leaves the project through a symbolic link or junction are refused. A `..` that stays inside the project (`scenes/../main.tscn`) is now accepted, and so is a path that is only read or referenced (`texturePath`, `scriptPath`, an autoload path, a `scene` to run) when a link on the way leads out of the project, so a shared `addons/` folder linked in keeps working. Every path field of a `batch_scene_operations` item is checked the same way, where 3.8.1 checked only containment. Path errors share one wording: `Invalid <field>: "<path>" resolves outside the project or is not a valid file name`.
- `stop_project` with nothing to stop returns `Nothing to stop: no runtime session is current.` in place of `No active Godot process to stop.`
- A `simulate_input` batch whose time budget (its waits and holds, plus its frames at 10 fps) is over 600 seconds is refused before anything is injected. A wait in milliseconds used to have no limit.
- A `simulate_input` `action` now does what its bound key does, in the UI too. A built-in `ui_*` action acts on the focused Control: `ui_accept` presses the focused `Button`, and `ui_up`, `ui_down`, `ui_left`, `ui_right`, `ui_focus_next` and `ui_focus_prev` move focus. In 3.8.1 an action only set the polled state through `Input.action_press`, so a `ui_accept` action changed nothing on screen. The `ui_text_*` editing actions still do nothing to a `LineEdit` or `TextEdit`, which read them only from key events. An action's handlers now run during its injection, before its result is read; in 3.8.1 no handler ran for an action at all.
- The script security scan and strict mode are removed. `run_script` and the first launch of a project now ask for one confirmation each per server session. See [The script security gate is removed](#the-script-security-gate-is-removed).

## The script security gate is removed

3.8.1 scanned GDScript before it ran. `run_script` sorted its source into Tier 1 (blocked), Tier 2 (asked) and Tier 3 (warned), and `run_project` scanned the project's autoloads and launch scene and listed what it found in `warnings`, refusing only under `GODOT_MCP_STRICT`. 4.0 removes the scan and replaces it with two plain confirmations. [`SECURITY.md`](../SECURITY.md) explains why and what is left.

| Item                                                                                             | 3.8.1                                                                                                 | 4.0                                                                                                                                                                       |
| ------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `GODOT_MCP_STRICT`                                                                               | Turned every Tier 2 finding into a block and refused launches on a scan finding or an unreadable file | Removed. It is ignored if set, with no startup message. Nothing replaces it                                                                                               |
| `GODOT_MCP_DISABLE_SECURITY`                                                                     | Turned the whole gate off, Tier 1 included                                                            | Removed. It is ignored if set, with no startup message. There is no gate to turn off                                                                                      |
| `GODOT_MCP_DISABLE_ELICITATION`                                                                  | Skipped the prompts, but strict mode overrode it and Tier 1 blocks still applied                      | Skips the confirmation prompts, and nothing overrides it. Set it if your client cannot display prompts, as for the 3.8.1 flag                                             |
| `run_script` with a Tier 1 primitive (`OS.execute`, `GDScript.new()`, `OS.call("execute", ...)`) | Refused, and never sent                                                                               | Runs after the one-time confirmation. The script has no scan result and no `warnings` entry for it                                                                        |
| `run_script` with a Tier 2 primitive (file writes, network, `set_script`)                        | Asked for confirmation on each such script                                                            | Asks once per project per server session, whatever the script holds                                                                                                       |
| `run_script` in an attached session                                                              | Scanned like any other script                                                                         | Asks for the same one-time confirmation. A launch confirmation does not count, because attach spawns nothing                                                              |
| `run_project` launch                                                                             | Scanned autoloads and the launch scene, listed findings in `warnings` and asked once per project      | Asks once per project per server session with no findings, as does `render_movie`, which is new in 4.0. An autoload that calls `OS.execute` launches with no scan warning |
| `.mcp/godot-runtime/scripts/`                                                                    | Each `run_script` call wrote a `.gd` copy and a `.policy.json` sidecar                                | Nothing is written. Files already there are left alone, and you can delete them                                                                                           |

The confirmation prompts say that the project's code, or the agent's script, runs with your user permissions. If you decline, the call is refused and the agent is told not to retry unless you ask. A prompt that is cancelled or goes unanswered refuses the call, and a client without elicitation proceeds with a warning.

## Removed tools

| Before                                        | Now                                                                                                                                                                                                                                                                                                                                                             |
| --------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `attach_project({ projectPath, bridgePort })` | `run_project({ projectPath, attach: true, bridgePort })`. `scene` is rejected with `attach: true` whenever it is given, and `background` and `profiling` when they are `true`, instead of being ignored. `false` is accepted. The launch confirmation prompt does not apply, because nothing is launched.                                                       |
| `detach_project`                              | `stop_project`. It detaches an attached session without killing the Godot process and reports `externalProcessPreserved: true`. After an attached session has ended by itself (you closed the game), `detach_project` used to succeed; `stop_project` now returns its `Nothing to stop: no runtime session is current.` error, and nothing is left to clean up. |

## Behavior changes in sessions

- `run_project` on a second project adds a session and makes it current. Sessions on other projects keep running.
- The runtime tools (`take_screenshot`, `simulate_input`, `get_ui_elements`, `run_script`), the profiling tools, `get_debug_output` and `stop_project` act on the current session. `switch_project({ projectPath })` changes which one is current. `stop_project` stops the current session and leaves none current.
- When no session is current, or the current game has exited, these tools return an error that lists the live sessions and points at `switch_project`. Nothing is picked for you.
- Scene and node edits are refused while any session is live on the project, current or not, and the refusal says to `switch_project` first when it is not the current one.
- The error for a bridge that never answered now names the port it waited on instead of `null`.
- A `run_project` that fails before it launches anything leaves the session that was current still current, and the session it would have replaced still running. A game whose bridge never answers is torn down, and the session that was current before the call is current again (a `run_project` on the current session's own project replaced that session first, so none is current). A game that exits during startup is not torn down: it stays current with its logs kept.
- A spawned `run_project` on a project where this server holds an attached session detaches that session first. The bridge in the Godot you launched is told to shut down, that Godot keeps running, and `message` says so. If its bridge does not acknowledge, `warnings` leads with that.
- For that game, the one that exits before its bridge is ready, `get_debug_output` reads the captured logs after the error and `run_project` can be retried without `stop_project`.
- When another host registered the session that blocks an edit, a render or a start, the refusal names that host and the owner file under `.mcp/godot-runtime/bridge/owners/` to delete if the session is known to be gone. A session registered from another host cannot be probed, so it counts as live.
- A spawned game is killed as a process tree on `stop_project` and when the server exits, so the Windows console wrapper and launcher scripts no longer leave the real game running with the bridge port held. Outside Windows the game and every headless run lead their own process group, so the kill reaches a wrapper script's engine too.
- A spawned game quits by itself within a few seconds of its server dying, including a server that was killed outright. An attached Godot is never told to quit.
- A bridge owner is judged by its pid and by the start identity it recorded for itself, which the operating system fixes when the process is created, so the owner file of a server that was killed, whose pid another process now holds, no longer blocks edits or strands the bridge. When the identity cannot be read the pid answer stands.
- A server that shuts down (`SIGINT`, `SIGTERM`, its client closing stdin, and on Linux and macOS its terminal closing with `SIGHUP`) stops its games, then waits up to 10 s for scene edits and asset imports still running to finish before it exits. One that has not finished by then is killed. No new headless run is started once the shutdown has begun. On Windows a closed console still exits at once.
- `run_project` ends its wait on the first answer from a bridge that refuses the session token, in either mode, and says a Godot left from an earlier session is listening on that port. It used to wait out the whole budget, up to 45 s with `attach: true`.
- In an attached session, a failed command ends the session only when the follow-up probe itself fails as a disconnect. A probe that times out is a game that is alive and busy, and the session stands.
